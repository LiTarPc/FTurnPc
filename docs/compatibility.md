# Совместимость ядер и профилей

[Все разделы документации](README.md)

Описаны ограничения FTurnPc на базовой ревизии `445d3b8` и сравнение с прежним сторонним ядром Free Turn Proxy v4.0.1. Это проверка исходников, не сертификация всех клиент-серверных комбинаций.

## Закреплённые ядра

Windows workflow использует:

- `LiTarPc/fturn-core`, commit `58d4f175d245c5773786e19ace454216c625f92f`, маркировка версии `4.1.3`;
- sing-box `1.14.0`.

Автоматические обновления FreeTurn идут из `LiTarPc/fturn-core`, включая preview. Номера форка и upstream не являются общей шкалой: `4.1.3` форка не доказывает наличие функций upstream `4.0.1`.

Установленное ядро может отличаться после замены. Обновление клиента не обновляет сервер на VPS.

## Режим и транспорт

`mode` выбирает тип локального релея и должен соответствовать серверу. `transport` определяет подключение к TURN-реле; это другой параметр.

| VPN/proxy-протокол | FreeTurn `mode` |
| --- | --- |
| VLESS, VMess, Trojan, Shadowsocks, AnyTLS, ShadowTLS, HTTP, SOCKS | `tcp` |
| WireGuard, Hysteria/Hysteria2, HY2, TUIC | `udp` |

Эта таблица описывает выбор режима, а не гарантирует поддержку каждого протокола. Прямой импорт URI реализован для VLESS, Trojan, Shadowsocks, Hysteria2/HY2 и TUIC; остальные варианты требуют подходящего JSON-конфига ядра.

Backend выводит режим из `wg` или `sb`, либо учитывает явное поле `mode`. Неверное сочетание может быть отклонено до запуска.

## Возможности нового upstream

| Возможность | Поддержка текущим FTurnPc |
| --- | --- |
| Обычный TURN relay через мессенджер, TCP/UDP | Основные CLI-флаги и логи совместимы по исходникам; нужен совместимый сервер |
| `provider direct` | Нет корректной поддержки: `-provider` не передаётся, готовность Windows требует TURN-маршрут |
| TCP `bond` | Не передаётся `-bond`, нет настройки профиля/UI |
| `rtpopus3` | Поле обфускации передаётся; профиль и ключ должны совпадать с сервером |
| KCP tuning, obf timing, DNS FreeTurn | Не управляются соответствующими полями UI |
| Новые `freeturn://` | Частичный импорт |

Upstream `direct` — прямое DTLS-соединение к серверу без TURN. Это не обход приложения/RU через sing-box `direct`. Upstream задаёт для него один поток по умолчанию, FTurnPc передаёт не меньше 10. Для `bond` нужна поддержка обеих сторон.

## Подтверждение Client ID

Upstream 4.0 добавил подтверждение Client ID с повторной отправкой. Это несовместимое изменение протокола.

Новый клиент ждёт ACK, серверный код закреплённой ревизии форка его не отправляет. Замена клиента на upstream при старом сервере без ACK не даёт рабочей сессии. Характерная ошибка: `server did not acknowledge client ID (server outdated?)`.

Новый upstream-сервер обрабатывает старую запись Client ID без ACK. Это обратная совместимость конкретного этапа авторизации, не гарантия всех настроек и протоколов.

В UDP upstream строка `Established DTLS connection` появляется до ACK. FTurnPc использует её как признак готовности: возможен преждевременный запуск sing-box при неуспешной авторизации. Наличие TUN не доказывает рабочий канал: проверяйте ошибки и реальный трафик.

## Импорт ссылок

Контейнер `freeturn://<base64url JSON>` распознаётся, но названия отдельных полей различаются:

| Поле upstream | Ожидает импорт FTurnPc | Результат |
| --- | --- | --- |
| Ссылка звонка мессенджера | `links` | Поле стороннего формата отличается; ссылка не переносится |
| `n` | `power` | Значение не переносится |
| `spc` | `streamsPerCred` | Значение не переносится |
| `mode` | Backend имеет `mode`, окно добавления его не копирует | Режим выводится из `wg`/`sb` |
| `bond`, `timing`, `kcp`, `dns`, `dnss`, `mcap` | Нет полного импорта | Настройки не применяются из ссылки |
| `provider` | Сохраняется | Не передаётся CLI |
| `peer`, `transport`, `obf`, `key`, `cid`, `wg` | Общие поля | Переносятся при обычном добавлении |

После импорта проверьте `Мессенджер (Links)`, мощность, `Streams/cred` и наличие `wg`/`sb`. Для TURN нужна ссылка звонка. Для `direct` ручное редактирование provider не устраняет ограничения запуска.

## Перед сменой ядра

Запишите источник и версии клиентского и серверного ядра, `mode`, обфускацию и VPN/proxy-протокол. Сохраните рабочую копию. Проверьте подключение, передачу данных, переподключение и отключение после замены. Если нужная пара не проверена, считайте замену экспериментальной и оставьте возможность отката.
